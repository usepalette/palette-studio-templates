# team/

How this team works together on the project — the operating manual. `context/stakeholders.md` says *who* is involved; this folder says *how* the team runs, so a new person (or a new agent) can get productive without asking around.

Keep it short and real — a half-filled page that reflects how you actually work beats an aspirational one.

## What lives here

- [`ways-of-working.md`](./ways-of-working.md) — cadence and rituals (standups, demos, reviews), communication channels, decision-making, working hours
- [`onboarding.md`](./onboarding.md) — how a new team member gets set up: access, tools, what to read first
- Add your own as the team needs them — e.g. `roles.md` (who owns what), `escalation.md`, `on-call.md`

## How to set this up

1. Fill in [`ways-of-working.md`](./ways-of-working.md) with how you actually meet, talk, and decide.
2. Fill in [`onboarding.md`](./onboarding.md) so the next joiner has a checklist to follow.
3. Add a doc for anything else your team leans on (roles, escalation paths, on-call).
4. If you're a solo operator and none of it applies, delete this folder — nothing else depends on it.

> The sample `ways-of-working.md` and `onboarding.md` describe a software build (they match the shipped example project). Swap the rituals, tools, and "definition of done" for whatever your team actually does — this folder works for any kind of team, not just engineering.

## What does *not* live here

- Who's who (names, roles, contacts) → [`../context/stakeholders.md`](../context/stakeholders.md)
- Decisions about *the work* → [`../decisions/`](../decisions/)
